# 润色和发布中文博文

## 先确认交付范围

- 只说「拟标题」时，读正文，给出建议标题和简短理由，不改文件。要求「改标题」时，更新标题及引用该标题的站内链接文字；没有要求润色就不改正文。
- 「润色」或「统一表达」时直接编辑指定文章。批量处理「剩下的文章」时，先盘点 `_posts/`，用当前对话、工作区和 Git 差异辨认已经处理过的文章。排除草稿、备份和不在范围内的文章。
- 给了原稿并要求写成 post 时，新增 `_posts/YYYY-MM-DD-slug.md`。只有用户要求提交、推送或发布时才执行对应 Git 操作；发布本站意味着推送到部署分支并检查 GitHub Pages。

## 读正文，再定标题

- 读完整原稿和少量同类近期文章，找出它真正写了什么：一次具体经历、一项取舍、一个对读者有用的做法，或读完一本书后改变的看法。
- 把主题和最具体的信息放进标题。例如「11 月工作重心：做产品」可改为「先做五十音 App：把开发、推广和变现走一遍」。同一项目的多篇文章，用各自的阶段或问题区分，例如初次尝试、重启后的日常、读完后怎样复用素材。标题不要暗示计划已完成或把手记写成教程。
- 原稿若是 `.pages`，优先取得完整的文本导出；本机有 Pages 时可用原生导出。新版文件是归档格式，不能直接用 `textutil` 取得正文时，可用可靠的 Pages 解析工具读取，并核对段落、列表和链接的顺序。预览图只用于核对，别把第一页当成全文。不要改写原文件。

## 保持作者自己的声音

- 保留第一人称、时间线和原稿的语气。开头尽量从一个动作、场景或发现写起：例如刚录完几条视频，或等 Codex 写原型时去录了读书视频。之后再写这件事引出的判断。
- 用具体的动作代替口号和术语。「提高执行力」可以落实为「先选一个渠道做深」；保留有用的专名、数字、原话、代码和阅读清单。短随笔不必硬加小标题，长文可以按转折或步骤分节。
- 分清亲身经历、作者的判断和下一步计划。不要为了让段落更顺就补写结果、对话、动机或细节；遇到含糊的专名或数据，保留能确定的意思。技术文中需要更正的命令或配置，先对照主文档；区分历史记录和给读者的操作建议。

## 检查成品与发布

- 新文章沿用站点的 front matter 和英文 slug。用户指定「今天」时，以站点时区（本仓库是 `Asia/Shanghai`）确定日期；旧文保留文件名、日期、永久链接、锚点和未涉及的 front matter。更新引用旧标题的链接文字，同时保留链接目标。
- 跑 `git diff --check` 和 `bundle exec jekyll build`。核对生成页的标题、日期、文章路径和相关站内链接；批量改稿时核对实际改动篇数及受影响的引用，留意丢失的图和锚点。
- 提交前查看暂存范围，只纳入用户要求的改动。推送前确认目标分支及一并推送的已有提交。本站由 `main` 的推送触发 GitHub Pages 工作流；推送成功和站点上线是两件事，报告已确认的状态。发布后提供文章链接或提交号。
